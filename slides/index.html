第一部分．聊天機器人 vs Agent

客服 vs 跑腿的助理

💬 聊天機器人

你問一句、它答一句，事情還是你自己去做。
單輪 LLM、情緒分類器也一樣：沒有用 LLM 控制流程，所以不算 agent。

🧭 Agent

你交代目標，它自己決定要查什麼、用什麼工具、做幾步，在迴圈裡一步步做完，做完或卡住再回報。

一句話：agent 就是讓 LLM 自己掌控流程、會用工具、在迴圈裡把任務做完的系統。

出處：Agent 定義

第一部分．聊天機器人 vs Agent

關鍵問題：誰決定下一步？

Workflow（工作流）Agent（代理）
誰決定路徑開發者事先寫好的程式路徑LLM 動態決定步驟和工具
優點對定義清楚的任務，可預測、一致適合步驟數量難以預測的開放式問題
代價路徑要事先寫好成本較高、錯誤可能累積

兩者合稱 agentic 系統。Anthropic 的建議：先找最簡單的解法，真的需要才加複雜度。

出處：Agent 定義來源｜Anthropic

第二部分．核心元件

一個 agent 由什麼組成？

🧠 模型

LLM 是大腦，負責推理和決策。

🛠️ 工具

可以呼叫的外部函式或 API，讓 agent 能查資料、做事。

📋 指令

清楚的指示和 guardrails，告訴 agent 該怎麼做、不能做什麼。

另一種說法（Lilian Weng）：LLM 大腦 ＋ 規劃 ＋ 記憶 ＋ 工具。兩種說法都在講同一件事，只是切法不同。

出處：Agent 定義來源｜OpenAI 指南來源｜Weng

第二部分．核心元件

工具：從房間伸出去的手

LLM 像讀過很多書、但被關在房間裡的人：不知道今天的新聞，心算也可能出錯。工具補上這些缺口。

Data 取資訊

查資料庫、讀 PDF、搜尋網頁

Action 做事

寄信、更新紀錄

Orchestration

把別的 agent 當成工具呼叫

Toolformer 讓模型自己學會何時呼叫哪個 API；Anthropic 則提醒工具說明（ACI）要寫得像給新同事的文件。

出處：工具使用來源｜OpenAI 指南來源｜Toolformer

第二部分．核心元件

記憶與規劃

📚 記憶

短期記憶：放得進 context window 的內容，像桌上攤開的筆記。
長期記憶：存在外部向量資料庫，需要時再檢索回來，像書櫃裡的資料夾。

🗺️ 規劃

任務拆解：把大任務拆成小步驟（例如 Chain of Thought）。
自我反思：回頭檢討、修正做法（例如 ReAct、Reflexion）。

常見誤會：LLM 不會自動記得上次聊過什麼，要靠系統把內容放回 context 或從長期記憶取回。

出處：記憶規劃

第三部分．ReAct 迴圈

ReAct：想 → 做 → 看，一直循環

Thought想：下一步該做什麼？
→
Action做：呼叫工具
→
Observation看：讀工具回傳的結果

↺ 回到 Thought，直到任務完成

像偵探辦案：先推理該查什麼 → 去調監視器 → 看到結果 → 再推理下一步。ReAct ＝ Reasoning ＋ Acting。

出處：ReAct 迴圈來源｜ReAct 論文

第三部分．ReAct 迴圈

為什麼有效？什麼時候停？

✅ 為什麼有效

推理幫助擬定和更新計畫；行動拿到外部真實資訊，減少幻覺。在 HotpotQA、Fever 上比純 chain-of-thought 更少幻覺；在 ALFWorld、WebShop 上，成功率比模仿學習和強化學習方法高出 34% 和 10%（絕對值）。

🛑 什麼時候停

agent 的「run」就是一個 while 迴圈，停在：呼叫最終輸出工具、模型不再呼叫工具、發生錯誤，或達到最大輪數。

迴圈不會自己停，一定要設停止條件，不然可能一直燒錢。

出處：ReAct 迴圈來源｜ReAct 論文

第四部分．工作流模式

五種常見的工作流模式

模式一句話例子
Prompt chaining 串接上一步的輸出是下一步的輸入，中間可加檢查關卡寫大綱 → 檢查 → 寫全文
Routing 分流先分類，再送到專門流程客服分一般／退款／技術
Parallelization 平行同時跑多個 LLM 再彙整（切塊或投票）一個回答、一個做內容把關
Orchestrator-workers中央 LLM 動態拆任務給 worker改動檔案數量不固定的程式任務
Evaluator-optimizer一個產生、一個評估，不合格就重做文學翻譯
出處：工作流模式來源｜LangGraph

第五部分．多代理

多代理：先單、後多

👔 Manager 模式

一個中央 agent 把其他專門 agent 當工具呼叫，由它統一跟使用者互動。例：翻譯請求分給西、法、義文 agent。

🤝 Decentralized 模式

agent 之間平起平坐，用 handoff 把控制權交出去。例：分流 agent 把訂單問題交給訂單管理 agent。

什麼時候該拆？提示裡 if-else 太多，或工具彼此太像。有些系統能管好超過 15 個清楚的工具，有些在不到 10 個重疊工具時就出問題。

出處：多代理來源｜OpenAI 指南

第六部分．風險與陷阱

把鑰匙交給新司機之前

  • 錯誤累積（compounding errors）：自主＝成本更高，一步錯可能步步錯 → 沙盒測試
  • 被攻擊：jailbreak、prompt injection 讓 agent 洩漏系統提示或亂做事
  • 分層 guardrails：相關性、安全分類、PII 過濾、內容審核、工具風險分級、黑名單／正規表達式
  • 人工介入：失敗超過門檻，或取消訂單、大額退款、付款這類高風險動作
  • 模型限制：context 長度有限、長期規劃困難、輸出格式不一定可靠
出處：風險與陷阱來源｜OpenAI 指南

總結

五句話帶走今天的內容

  • Agent ＝ LLM 自己決定下一步，用工具在迴圈裡把任務做完。
  • 核心零件：模型、工具、指令（也可以說是大腦＋規劃＋記憶＋工具）。
  • ReAct：Thought → Action → Observation，記得設停止條件。
  • 流程固定就用 workflow；先把單一 agent 做好，再考慮多代理。
  • 自主有代價：分層 guardrails ＋ 高風險動作交給人。
出處：Agent 定義ReAct 迴圈多代理風險與陷阱

小測驗（點題目看答案）

考考你

Q1．一個只會判斷評論是正面還是負面的情緒分類器，算 agent 嗎？

不算。它沒有用 LLM 控制流程執行，也不會用工具採取行動。

Q2．ReAct 迴圈中，讀取工具回傳結果的那一步叫什麼？

Observation（看）。順序是 Thought → Action → Observation。

Q3．客服系統先判斷問題是「退款」還是「技術支援」，再交給不同流程，這是哪種模式？

Routing（分流）。

Q4．由一個中央 agent 把其他 agent 當工具呼叫，是哪一種多代理模式？

Manager 模式。另一種是 agent 之間互相 handoff 的 Decentralized 模式。

Q5．agent 要幫使用者付款之前，最好怎麼做？

觸發人工介入：付款屬於高風險、不可逆的動作，要讓人確認。
